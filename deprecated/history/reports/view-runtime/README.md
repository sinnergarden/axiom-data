# View runtime closure

The public required-View operation validates one concrete Snapshot, groups compatible requests into bounded batches of at most 50 securities, and publishes one immutable artifact per security. The initial execution map is in `execution-map.md`. This change keeps the existing PIT, revision, missing, provenance, and artifact rules; loaders for published older versions remain available.

The full-history 1/10/50 build times were 135.72/75.61/77.63 s for adjusted, 96.45/97.76/not run s for replay, 35.81/36.77/not run s for Qlib, 263.42/329.21/not run s for financial, and 136.76/129.39/not run s for event. The isolated dependency-validation costs in the table are **not** added for every View in one public operation. The financial final probe used one validated Reader for the 1-View and 10-View measurements. The formal full-Snapshot operation has a separate, previously measured initialization cost and was not run here.

The old financial profile recorded 50.27 s in 1,890 complete-universe `active_members` calls over 946 days. Repeating that scan for roughly 2,887 days explains most of the observed 160 s per later security. The operation now keys the complete selected group by immutable state, policy, group, and session, validates it before symbol projection, and reuses the result across bounded batches. The cache has an 8,192-entry limit and lives only in the checked Reader's operation. Industry source rows are prepared once. A state change misses the cache; a conflict in an unrequested member still fails.

The final financial probe used the concrete candidate `snapshot-1d69dc236a358f1627ae91080c33cf993b9e2acb55bbd2c2cb7a37129ce6b5a5`, 2014-10-31–2026-09-11, and isolated output under workspace `review/view-operation-batch-20260924/financial-v4-final-2014-2026`. The 1-View build wrote 0.139 GB, read 19.25 GB logically and 0.574 GB physically. The 10-View batch wrote 1.384 GB, read 20.51 GB logically and 0.009 GB physically in the warm-cache run. Its first View took 233.04 s; the remaining nine took 9.55–11.79 s each. Full 2,887-row output for `000001.SZ` equals the previously validated serial result, including values, PIT, missing and provenance. Three dates for each of the first and last batch securities equal direct serial projection. Completed resume invoked zero builders: 1.31 s for one View and 14.87 s for ten.

At 10.11 s marginal time, 3,580 securities account for about 10.1 h. The 10-View first cost includes one-time full-member state preparation and industry source loading; the old profile accounts for roughly 154 s and 23 s of those costs. The remaining measured cost suggests roughly 50–60 s of preparation per 50-security batch, yielding an **estimated 11–12 h** for this family, excluding shared full-Snapshot initialization. This is an extrapolation from a warm 1/10 sample, not a full 3,580-View execution or a guaranteed deadline. The current financial v4 output is about 139 MB per security in this sample, implying roughly 498 GB for 3,580 securities; disk capacity must be checked before a separate bulk authorization.

The measured market batches read 22.26 GB logically for replay and 6.19 GB for Qlib; event read 33.51 GB logically. Their warm physical reads were close to zero after the checked Reader and first source traversal. Adjusted's 50-View batch read 12.58 GB logically. Build publication uses one business projection per new View; current loaders check declared file integrity and structure, and completed resume enters no builder. Older declared View versions keep their historical loaders.

Validation: 55 View/financial/event tests passed in 24.8 s, and 34 legacy-read, resume, validation and publication tests passed in 15.6 s: 89/89 targeted PASS. The complete financial fixture compares serial and batch artifacts byte for byte, and the output-shape census confirms no full-index membership array is copied into financial v4 Views. The final real View manifests' implementation digests match the current source tree at implementation commit `8fa569e0504c5a2459a34973f6fcd80510e6a1b3`; the one-off probe logged the parent HEAD at launch before that unchanged source tree was committed. No formal data, candidate, checkpoint, or paused bulk operation was modified.

Separate source-scope finding: the frozen formal financial View plan starts 2014-01-02, while the candidate's requested universe coverage does not begin until 2014-10-31. That plan still fails `INSUFFICIENT_SCOPE: universe dates`; this runtime ticket does not change its scope or source semantics. The performance probe therefore used the covered full-history interval beginning in 2014.
