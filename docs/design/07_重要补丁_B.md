# 07_重要补丁_B：Axiom 与 LEAN 的架构对照与设计裁决

> 状态：Architecture Patch\
> 目的：补充 Axiom 总体设计，明确哪些部分应直接借鉴成熟量化框架 LEAN，哪些部分应坚持 Axiom 自己的设计。\
> 适用范围：axiom-data / axiom-engine / axiom-research / axiom-ui 及跨模块协议设计。\
> 本补丁不讨论 Agent-native 开发、Harness 或治理机制，仅讨论量化系统本体。

---

## 1. 核心结论

Axiom 与 LEAN 在 **Engine / 交易执行侧高度相似**，真正差异最大的是 **Data、Research 和 Artifact Identity**。

可以将 Axiom 的总体方向概括为：

```text
Axiom
≈ LEAN-like Engine
+ Qlib-like ML Research
+ 更严格的 PIT / Data / Artifact Governance
+ A股专项交易语义
```

LEAN 的核心问题是：

> 如何让一个 Algorithm 在 backtest 和 live 中可靠运行？

Axiom 的核心问题更进一步：

> 一个策略如何从可信数据出发，经过 Feature、模型、Signal、回测和发布，最终以完全可追溯的方式进入 shadow / real？

因此，Axiom 不应该重新发明一整套事件引擎和交易抽象；但也不应该退化成“给一个 DataFrame，然后直接回测”的传统量化框架。

---

## 2. Axiom 与 LEAN 的总体对照

| 维度 | Axiom | LEAN | 设计裁决 |
|---|---|---|---|
| 核心定位 | A股日频、ML/排序、研究→回测→实盘 | 通用多资产事件驱动量化引擎 | 目标不同 |
| Data | PIT、revision、snapshot、evidence、drift | 规范化交易数据集 | Axiom 保留更强治理 |
| Research | Feature/Label/Model/Signal 一等资产 | Notebook + Algorithm/ML workflow | Axiom 更结构化 |
| 决策链 | Feature→Prediction→Signal→Target→Risk→OrderIntent | Universe→Alpha→Portfolio→Risk→Execution | 思路高度一致 |
| Backtest/live | 同一决策核心，替换外部 adapter | 同一 Engine，替换 handler | 直接借鉴 |
| 撮合/成本 | A股专项实现 | Fill/Fee/Slippage/BuyingPower 等成熟 Reality Models | 重点借鉴 |
| 状态/账本 | 显式 durable ledger、恢复、幂等、对账 | Portfolio/Transactions/Brokerage state | Axiom 更强调运营恢复 |
| Version/lineage | Snapshot/Release/Run 强身份 | 较自由，更多依赖 project/config/object store | Axiom 保留 |
| UI | Evidence / Research / Trading Console | QuantConnect 平台 UI | Axiom 更偏 forensic |

---

## 3. Data：不能照搬 LEAN

LEAN 的 Data 层主要回答：

> Engine 如何按时间正确获得行情、Universe、公司行动和证券属性？

Axiom Data 还必须回答：

```text
这个值来自哪里？
供应商是否后来修改过？
某个 revision 当时是否真的可知？
系统第一次什么时候看到它？
某个研究究竟使用的是哪一个数据状态？
```

因此 Axiom 保留：

```text
Raw 原响应 + fetch 日志
→ 版本化 Canonical Parquet
→ 一个 DataSnapshot（按域内嵌完整分区与来源）
→ Reader + QuerySpec；必要稳定派生先为函数/缓存
→ Fact / Market 读取；Qlib 在真实需要时导出
```

以及：

- Source Profile；
- PIT capability；
- revision / first-observed；
- source evidence；
- supplier drift；
- immutable snapshot；
- 实际用途/范围检查及缺口解释，不建通用 certification/admission 平台。

[Data 个人版](02_axiom_data.md) 保留 DomainCommit 的逻辑边界，首版不独立发布；ViewRef 可内嵌 Snapshot + QuerySpec，也不逐查询发布 artifact。代码先固定为可恢复 commit、依赖锁与实际配置，重要发布再可选归档。evidence 只按目标需求保留，不追求全历史 verified。market-public 与 system-observed 是不同问题，补公开证据不会替代 operational 的实际到达历史。

### 3.1 Qlib 的定位

Qlib 不能继续像旧 Qsys 那样同时承担：

- 数据事实来源；
- Feature 读取层；
- Label 计算源；
- Universe 权威；
- Backtest 行情源。

Axiom 中：

> **QlibView 是绑定 DataSnapshot 的按需导出/读取格式，事实仍由 Snapshot 固定。早期个人首版可按任务启用；本轮用户已经明确启用，Qlib 导出、实际消费者及等价验证已纳入当前交付并完成。普通采集和 Reader 不依赖 Qlib 运行时。**

必须可以回答：

```text
QlibViewRef
= DataSnapshot
+ Universe
+ PIT / cutoff policy
+ exporter code/config
+ field mapping
```

---

## 4. Universe：采用 LEAN 的动态思想，但保留 Axiom 的证据语义

LEAN 已经明确避免使用当前指数成员回测历史。

Axiom 同样要求动态 PIT Universe，但还要保存：

```text
effective_from / effective_to
available / announced time
first_observed
source evidence
snapshot identity
```

因此区别不是“Axiom 比 LEAN 更懂 survivorship bias”，而是：

> LEAN 要求使用正确的历史 Universe；\
> Axiom 还要求能够证明为什么它被认为正确。

当前 operational universe 和 historical PIT universe 必须严格分离。

---

## 5. Research：Axiom 比 LEAN 更强调 ML 资产化

LEAN Research 允许：

```text
Notebook
→ Feature engineering
→ Model training
→ 保存模型或 prediction
→ Backtest / Live
```

这很灵活，也支持提前计算 prediction 再回测。

Axiom 应保留这种灵活性，但把正式研究资产化：

```text
Hypothesis
→ fixed DataSnapshot/View
→ FeatureRelease
→ LabelBuild
→ TrainingDataset
→ ModelRelease
→ OOS SignalRun
→ SignalEvaluation
→ BacktestRun
→ StrategyRelease
```

重点不是制造大量 metadata，而是防止旧 Qsys 已出现的问题：

- label 参数和真实公式不一致；
- Feature 名相同但实现不同；
- Universe / split / preprocessing 分散；
- 回测收益无法还原实际训练输入；
- 重跑时动态读取 latest/current。

### 5.1 SignalRun 是一等资产

推荐模式：

```text
训练 / OOS 推理一次
        ↓
     SignalRun
        ↓
IC / RankIC / Recall@K
        ↓
不同组合 / 风控 / 回测
```

这与 LEAN 推荐“Research 预计算 prediction，回测时作为数据流输入”的思想一致。

区别在于 Axiom 将 SignalRun 正式定义为带 lineage 和 OOS 语义的资产。

---

## 6. Engine：应大量借鉴 LEAN

这一层最不应该重新发明轮子。

Axiom 决策链：

```text
Feature
→ Prediction
→ Signal
→ TargetPortfolio
→ Risk
→ OrderIntent
```

LEAN Algorithm Framework：

```text
Universe
→ Alpha / Insight
→ PortfolioTarget
→ Risk
→ Execution
```

两者高度一致。

### 6.1 Core 的原则

Core 负责确定性决策：

```text
Market / Fact Input
+ AccountState
+ StrategyState
+ StrategyRelease
→ Feature / Prediction / Signal
→ TargetPortfolio
→ Risk-adjusted Target
→ OrderIntent
→ New StrategyState
```

Core 不负责：

- systemd；
- CLI；
- latest/current/pointer 解析；
- 数据库；
- Broker API；
- 网络；
- 真实或模拟成交；
- 文件发现；
- Qlib 路径管理。

Core 不需要知道自己运行在：

```text
backtest
shadow
real
```

这些由 Runtime 选择 Adapter。

---

## 7. Runtime / Trade：采用 LEAN Handler 思想

LEAN 的成熟设计本质上是：

```text
相同 Algorithm
+ 不同 DataFeed
+ 不同 TransactionHandler
+ 不同 Clock / RealTimeHandler
```

Axiom 对应为：

```text
Backtest
  HistoricalClock
  + MarketReplayView
  + SimBroker
  + RunArtifactStore

Shadow
  LiveClock
  + LiveMarketFeed
  + SimBroker
  + DurableStateStore

Real
  LiveClock
  + LiveMarketFeed
  + RealBroker
  + DurableStateStore
```

共享：

```text
StrategyRelease
→ Core Decision Chain
→ OrderIntent
```

不同：

```text
事件从哪里来
如何成交
状态保存在哪里
```

### 7.1 Runtime 不单独拆 repo

Runtime 属于 Engine / Trade 的 application layer，不需要再创建一个独立仓库。

推荐逻辑结构：

```text
axiom-engine/
  core/
  runtime/
  brokers/
  execution/
  accounting/
  ledger/
  cli/
```

实际仓库命名可以保持当前 Axiom 规划，但职责边界应保留。

---

## 8. Backtest：只保留一套正式回测语义

不再设计独立的“fast backtest”和“parity backtest”两套逻辑。

Research 的高频流程应该是：

```text
Feature / Model
→ OOS SignalRun
→ Signal Evaluation
→ 统一 Backtest Engine
```

研究性能通过以下方式优化：

- SignalRun 复用；
- Feature / Dataset cache；
- 避免重复训练；
- 只回测必要阶段；
- 增量 artifact。

而不是再创建一套近似回测引擎。

正式回测、shadow、real 必须复用：

```text
Signal → Target → Risk → OrderIntent
```

以及相同的交易规则语义。

---

## 9. Reality Modeling：直接学习 LEAN 的抽象

Axiom 不应重新发明交易现实模型。

建议沿用类似 LEAN 的结构：

```text
TradabilityModel
FillModel
FeeModel
SlippageModel
LotSizeModel
BuyingPowerModel
SettlementModel
CorporateActionAccounting
```

A股第一阶段至少覆盖：

```text
T+1
停牌 / 缺价
涨跌停
100股整数手
手续费 / 印花税
分红送转
退市
成交量限制
```

后续再增加：

```text
冲击成本
更细撮合模型
```

不需要建设完整交易所级 matcher。

---

## 10. Ledger：Axiom 应比 LEAN 更强调 durable operational semantics

Axiom 实盘必须明确处理：

```text
Intent persisted
→ submit
→ broker ack
→ OrderEvent
→ FillEvent
→ AccountEvent
→ ledger
→ projection
→ reconciliation
```

特别必须回答：

```text
Broker 收到订单，但本地进程在确认前崩溃怎么办？
同一回报收到两次怎么办？
部分成交怎么办？
重启后如何知道哪些订单已经提交？
Broker position 和本地 ledger 不一致怎么办？
```

因此：

- Backtest event log 是不可变运行产物；
- Real Trade ledger 是事务性、可恢复的权威状态；
- UI 不能成为账本；
- Core 不能拥有账本。

---

## 11. Artifact / Version Identity：继续坚持 Axiom

LEAN 给用户较大自由度管理：

```text
project code
config
model files
Object Store
backtest artifacts
```

Axiom 不应该回到这种松散模式。

正式运行应明确绑定：

```text
DataSnapshot
FeatureRelease / FeatureBuild
TrainingDataset
ModelRelease
SignalRun
StrategyRelease
Core / Engine Release
ResolvedRunPlan
BacktestRun / ShadowRun / RealRun
```

核心原则：

> 路径不是版本；`latest/current/mtime` 不是正式身份。

一次固定计划（离线实验或长服务的 session/决策批次）启动后：

```text
resolve once
→ validate
→ freeze
→ run
```

该计划执行期间禁止再次解析动态 pointer。长服务下一批次可重新解析并 preflight；保存批次到实际 refs 的映射，不把启动时 Snapshot 永久锁住，也不使用最终 Snapshot 覆盖旧批次来源。具体以总纲 §11.1 和 Runtime §4.3 为准。

---

## 12. UI：更偏 Evidence Console

Axiom UI 不只是交易看板。

应该能从同一运行身份查看：

```text
Data/PIT evidence
→ K线 / 财务事实
→ Feature
→ Prediction
→ Signal
→ Target
→ Risk
→ OrderIntent
→ Fill
→ Position / PnL
```

例如点击：

```text
某股票 / 某日 / 某次 Run
```

能够回答：

```text
当时看到什么数据？
Feature 为什么是这个值？
为什么进入 / 离开 Top5？
模型 score 是多少？
最后为什么下了这个单？
实际成交怎样？
```

UI 只消费正式 artifact / view，不重新实现业务计算。

---

## 13. Axiom 应直接借鉴 LEAN 的部分

以下部分应将 LEAN 作为主要 reference architecture：

1. Engine handler / adapter 结构；
2. Backtest / live 共用事件引擎；
3. Security / Portfolio / Order / Fill 状态模型；
4. Fill / Fee / Slippage / BuyingPower / Settlement Reality Models；
5. Signal/Insight → PortfolioTarget → Risk → Execution 分层；
6. Clock / DataFeed / Broker 与决策核心解耦。

原则：

> 在 Engine 层不要为了“自主设计”而创造与成熟框架完全不同的一套抽象。

---

## 14. Axiom 不应照搬 LEAN 的部分

### 14.1 Data Governance

保留：

```text
PIT
revision
first-observed
按需 source evidence
immutable snapshot（内嵌域段）
supplier drift
实际用途/范围检查；不建通用认证平台
```

### 14.2 ML Research Lifecycle

保留：

```text
FeatureRelease
Label
TrainingDataset
ModelRelease
SignalRun
OOS evidence
StrategyRelease
```

### 14.3 Artifact Identity

坚持：

```text
immutable identity
explicit lineage
resolve once
no latest/current/mtime
```

而不是主要依靠目录和用户纪律管理版本。

---

## 15. 对 Axiom 总体设计的最终补丁

Axiom 的核心架构方向保持不变，但 Engine 设计应明确采用以下原则：

```text
DataSnapshot
        ↓
ResearchFactView
        ↓
Feature / Label / Model
        ↓
SignalRun
        ↓
StrategyRelease
        ↓
        Core
Signal → Target → Risk → OrderIntent
        ↓
Runtime / Broker / Ledger
        ↓
Backtest / Shadow / Real
```

其中：

```text
Data 负责事实可信。
Research 负责预测假设和证据。
Core 负责唯一决策语义。
Runtime 负责运行环境选择和事件驱动。
Broker / Ledger 负责现实世界与持久状态。
UI 负责只读观察和解释。
```

最重要的新增原则：

> **Axiom 的 Engine 不追求原创架构。凡是 Clock、Event Loop、Order、Portfolio、Fill、Broker、Reality Model 等成熟交易引擎问题，优先参考 LEAN 的已验证设计；Axiom 的主要差异应集中在 PIT 数据可信、ML Research 生命周期、Artifact Identity 和 A股专项语义。**

这可以避免 Axiom 把大量精力投入到成熟框架已经解决的问题，同时保留 Qsys 实践中真正暴露出来、LEAN 公共架构没有替我们解决的问题。
