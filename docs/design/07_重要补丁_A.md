## 0. 为什么需要这个补丁

原设计包的核心职责划分总体成立：

- Data 管可信事实、PIT、Snapshot/View；
- Research 管 Feature/Label/Dataset/Model/Signal 的研究定义、训练、评估和发布；
- Core 管共享计算与投资决策语义；
- Trade 管 runtime、统一回测、Broker、账户与账本；
- UI 只读展示。

但在实施顺序和部分文字描述上存在一个足以误导 Worker 的歧义：

> “Research 先于 Core”容易被理解成“Research 可以先实现一套自己的 Feature/Inference/Signal executor，再由 Core 后续抽取”。

**此理解错误。**

如果这样施工，会形成：

```text
research executor
        +
core executor
```

两套计算语义，重新制造 Qsys 中最需要避免的重复实现、语义漂移和后续迁移成本。

本补丁正式消除这一歧义。

# 1. 物理仓库改为四仓

原总纲中的“五个独立仓库”调整为：

```text
axiom-data

axiom-ui
```

其中原来的 `axiom-core` 与 `axiom-trade` **合并为一个物理 repo：`axiom-engine`**。

建议结构：

```text

  runtime/

    adapters/
    broker/

    reconciliation/
    reporting/
    deploy/
```

## 1.1 合仓不等于职责合并

`core` 与 `runtime/trade` 仍然是两个明确的逻辑边界：

### Engine/Core

负责：

```text
FeaturePlan + FactBatch
    → FeatureFrame

ModelHandle + FeatureFrame
    → PredictionFrame

SignalPlan + PredictionFrame
    → SignalFrame

SignalFrame + AccountState + StrategyState + DecisionContext
    → TargetPortfolio + OrderIntent + NewStrategyState + DecisionTrace
```

不负责：

- Data I/O；
- Label；
- Dataset split；
- 模型训练；
- 实验管理；
- Broker；
- 撮合；
- ledger；
- scheduler；
- 回测事件循环。

### Engine/Runtime

负责：

- ResolvedRunPlan；
- Historical/Live clock；
- 唯一正式 backtest；
- SimBroker / RealBroker；
- accounting；
- ledger；
- recovery / reconciliation；
- shadow / real；
- 标准账户绩效报告。

因此，物理上是四仓，逻辑上仍保留：

```text
Data
Research
Engine/Core
Engine/Runtime
UI
```

## 1.2 版本轴仍然独立

即使 Core 与 Runtime 同 repo，也保留独立的语义版本：

```text
Core API / Core semantic version
Runtime / execution semantic version
```

例如修复 QMT Broker adapter，不应自动改变 Feature execution 的语义身份。

# 2. Research 与 Engine/Core 的正式边界

这是本补丁最重要的裁决。

一句话：

> **Research 定义“算什么、为什么算、如何训练和比较”；Engine/Core 唯一负责可复用的“怎么算、怎样从信号产生决策”。**

---

## 2.1 Research 负责什么

Research 是变化最频繁的仓库。

负责：

### Feature 研究定义

例如：

```text
financial_quality_v3
momentum_60d
holder_concentration_change
entry_heat
```

Research 决定：

- Feature 的业务含义；
- 输入字段；
- window / lag；
- Feature 组合关系；
- reference universe；
- missing/outlier policy；
- 哪些 Feature 进入哪个模型；
- FeatureRelease。

### Label

包括：

- horizon；
- return start/end；
- price basis；
- benchmark；
- maturity；
- missing/delisting policy。

**Label 完全属于 Research。**

它不是生产 Feature execution 的一部分，不应进入 Core。

### Dataset / Split

Research 负责：

- sample keys；
- universe filtering；
- train/validation/OOS；
- purge；
- maturity；
- fitted preprocessing 的训练范围；
- rolling fold 定义。

### Training

Research 负责：

- LightGBM / Ranker / DNN 等训练；
- loss / hyperparameters；
- seed；
- rolling retrain；
- model selection；
- TrainingDataset → ModelRelease。

### Experiment / Evaluation

Research 负责：

- IC / RankIC；
- TopK；
- NDCG；
- 消融；
- phase / seed / year stability；
- feature/model comparison；
- negative experiment；
- Evidence；
- 报告。

### Artifact 与 Cache

Research 负责自己的：

```text
FeatureRelease
FeatureBuild
LabelBuild
TrainingDataset
ModelRelease
SignalRun
SignalEvaluation
StrategyRelease
```

以及这些 artifact 的 identity-bound reuse/cache。

---

# 3. 哪些 Feature 逻辑属于 Core

不是“Feature 全放 Research”，也不是“Feature 全放 Core”。

正确拆分是：

## 3.1 通用算子属于 Engine/Core

例如：

```text
shift
rolling mean/std/min/max
EMA
pct_change
rank
zscore
winsorize
neutralize
safe divide
group transform
schema alignment
missing handling primitives
```

只要它是跨 Feature、跨模型、Research 与生产都需要共享的稳定计算语义，就应进入 Core。

## 3.2 Feature recipe / 专用插件属于 Research

例如：

```text
financial_quality_v3 =
    zscore(cfo_to_profit)
  + zscore(-receivable_growth)
  + zscore(cash_to_short_debt)
```

其：

- 经济假设；
- 参数；
- 依赖字段；
- operator graph；
- 输出 schema；

属于 Research 的 `FeatureRelease / FeaturePlan`。

如果某 Feature 确实包含无法用现有通用 operator 表达的专用纯计算代码：

```text
research 发布 frozen feature plugin
→ Engine/Core 通过稳定 ABI 执行
```

**专用插件的业务实现仍由 Research ownership；执行 ABI 与执行器由 Core ownership。**

新增一个 Feature 原则上不应要求修改 Core。

只有出现真正新的通用计算能力时才升级 Core。

---

# 4. Research 不得拥有第二套执行器

以下实现禁止进入 Research：

```text
research/features/executor.py     # 与 Core 平行的执行器
research/model/inference_engine.py
research/signal/runtime.py
research/backtest/*
research/broker/*
```

Research 可以有 service/orchestration：

```python
build_features(...)
generate_signal(...)
```

但这些 service 的语义是：

```text
Research resolve recipe/artifacts
→ Data Reader 读取事实
→ Engine/Core execute_feature_plan()
→ Research 保存 FeatureBuild

Research 训练
→ 保存 ModelRelease

Research 加载 ModelRelease
→ Engine/Core predict()
→ Engine/Core combine_signals()
→ Research 保存 SignalRun
```

因此：

> Research 能“run experiment”，不等于 Research 自己拥有计算 runtime。

它是研究编排方和 artifact owner，而不是第二个 Core。

---

# 5. Training 与 Inference 的边界

这一点必须固定。

## Research

```text
Dataset
→ fit / train
→ fitted preprocessing state
→ model bytes
→ ModelRelease
```

## Engine/Core

```text
ModelHandle
+ frozen preprocessing state
+ FeatureFrame
→ PredictionFrame
```

Core **不训练**。

Research **不另写 production inference path**。

Research 在生成 OOS SignalRun 时，也调用和未来生产相同的 Core inference ABI。

这样才能保证：

```text
Research historical OOS inference
==
Backtest inference
==
Shadow inference
==
Real inference
```

在相同输入下语义一致。

# 6. Signal 的边界

## Research 负责

定义：

```text
score semantics
60d model
180d model
daily zscore
0.5 * z60 + 0.5 * z180
```

即 `SignalPlan / SignalSpec`。

## Engine/Core 负责

执行通用：

```text
join
rank
zscore
weighted combine
missing/stale handling
```

并产生标准 `SignalFrame`。

Research 保存实际 OOS `SignalRun`。

---

# 7. Portfolio / Rebalance / Risk 的边界

具体策略 recipe 仍属于 Research：

```text
Top5
equal weight
weekly
允许空仓
max single-name exposure
score retention
```

Research 最终把这些冻结为 `StrategyRelease` 中的 policy definition/config/plugin。

但是：

```text
portfolio policy executor
rebalance executor
risk executor
TargetPortfolio
account-aware delta
OrderIntent planning
strategy-state transition
```

属于 Engine/Core。

因此不能在 Research 写一个简化版 Top5 backtest，再等 Engine 后续重写。

---

# 8. Cache 的正确归属

Research 可以而且应该有 cache / reuse。

但第一原则是：

> **正式 artifact 本身就是最重要的 cache。**

例如：

```text
FeatureBuild
LabelBuild
TrainingDataset
ModelRelease
SignalRun
```

如果完整 identity 一致，可直接复用。

FeatureBuild identity 至少绑定：

```text
Data/View refs
FeatureRelease
scope + lookback
PIT/cutoff
reference universe
implementation/package
```

不要第一版建设：

- 通用 DAG cache engine；
- distributed cache；
- Feature Store 服务；
- 自动全图 invalidation 平台；
- 复杂 GC 系统。

Research cache 决定“要不要重新执行”。

真正的 Feature/Inference/Signal 计算语义仍由 Core 执行。

# 9. 修正后的实施顺序

原文中“Research 先于 Core”改成更精确的：

> **Research recipe/contracts discovery 先于 Core；Research 的正式 Feature/Inference/Signal 执行不能先于 Core。**

正式顺序：

---

## Phase A — Data

完成足够支持第一个真实策略的：

```text
Raw/fetch + Canonical Parquet
一个 DataSnapshot manifest（内嵌域段与完整分区）
ResearchFactView = Snapshot + QuerySpec + Reader
PIT membership（历史证据不足则明示 best-effort）
MarketReplayView（进入账户回放时补齐执行事实）
required stable derived（先纯函数/缓存）
QlibView（已实现；任务需要此 backend 时显式导出）
```

---

本节给出依赖顺序。当前用户已要求完整Data，交付边界包含财务/股东、PIT与供应商生命周期/成员、Reader与Qlib实际消费及双教程，详见[Data设计](02_axiom_data.md)与[实际交付](../../DELIVERY.md)。DomainCommit保留逻辑含义但内嵌Snapshot，ViewRef可内嵌查询；不要求独立Derived发布、通用admission/evidence平台或每次源码打包。可恢复源码、依赖锁、实际配置固定构建。四仓裁决、Research定义/Core执行、Runtime唯一回测的边界保持不变。

## Phase B — Research R0：真实 recipe 与 contracts

不追求完整运行。

Financial RC 60d/180d 保留为财务研究的纵向案例；个人 Data 首版可先用仅依赖市场事实的简化研究路径验收。尚未接入财务不阻止行情版交付，但也不能称为 Financial RC 已可运行。进入该财务研究案例时，确定：

```text

DatasetSpec

```

同时完成 legacy forensic：

- 真实 Feature；

- split；
- fold；
- zscore；
- 50/50 blend；
- PIT；
- baseline refs。

本阶段**不实现 Feature executor，不实现 inference executor，不实现 backtest**。

R0 的核心产物之一是：

```text

```

即第一个真实策略到底需要 Core 提供哪些 operator / ABI。

# 11. 四仓的变化频率

预期：

| Repo | 变化频率 | 典型变化 |
|---|---|---|
| axiom-data | 低 | 新数据源、PIT 修正、事实 contract |
| axiom-engine | 低～中 | 新通用 operator、执行语义、Broker/accounting correctness |
| axiom-research | 高 | Feature、Label config、模型、Signal、策略 recipe、实验、报告 |
| axiom-ui | 低～中 | 新图表、查询与展示 |

判断架构是否健康的一个简单指标：

> 日常尝试一个新的 Feature、Label、模型或组合，大多数情况下只修改 `axiom-research`。

如果 Research 每次实验都要求修改 Data 或 Engine，应先判断是否发生了职责泄漏。

# 13. 架构不变量

以下作为后续 code review 的 blocking 条件：

1. Data 不拥有预测 Feature、Label、模型或策略。
2. Research 不直接读 Data 私有目录作为正式输入。
3. Research 不拥有与 Engine/Core 平行的 Feature executor。
4. Research 不拥有与 Engine/Core 平行的 production inference executor。
5. Research 不拥有第二套正式 backtest。
6. Engine/Core 不训练模型。
7. Engine/Core 不定义具体研究结论或偷偷寻找 latest model。
8. Engine/Runtime 不重新实现 Feature / Signal / portfolio 研究逻辑。
9. UI 不重新计算业务真相。
10. Feature/Label/Model/Signal/Strategy 的变化不应原地覆盖旧 artifact。
11. Backtest / shadow / real 在相同输入下必须共享同一 Core 决策语义。
12. 任何“临时实现以后再抽象”的方案，如会产生第二套业务计算路径，默认拒绝。

# 15. 最终原则

> **Data 描述世界。**\
> **Research 定义假设、训练与证据。**\
> **Engine/Core 唯一实现共享计算与决策语义。**\
> **Engine/Runtime 唯一负责历史与真实世界中的执行。**\
> **UI 只负责把已经发生和已经保存的东西看清楚。**

Axiom 的目标不是模块越多越正规，而是：

> **研究可以频繁变化，而事实、计算语义和交易语义不会因此分叉。**
